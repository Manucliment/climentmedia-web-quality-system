## §82 · The door said the host's 404 had been answered, and nobody had asked the host

A site went live with its receipt at PASS and the served-files check (G11) at PASS. The first
probe after the upload, done by hand, found that **every broken URL showed the web server's own
generic 404 page** — about 800 bytes, no menu, no way back into the site — and that the error page
requested directly returned **500**. The site's `.htaccess` had passed its bank of 100 cases
against a real Apache 2.4.

**Why the bank could not see it.** The host runs LiteSpeed, and LiteSpeed does not fill
`REDIRECT_STATUS` the way Apache does. Measured on production, one request per origin of the error:

| How the 404 was produced | Page served |
|---|---|
| a `RewriteRule … [R=404]` or `[G]` | the site's own |
| a file that does not exist | the server's generic one |
| a `RedirectMatch 404` | the server's generic one |

A rule meant to answer 404 to direct requests for the error page *"except inside the
ErrorDocument"* was written as `RewriteCond %{ENV:REDIRECT_STATUS} ^$`. On LiteSpeed that variable
arrives **empty** in the error subrequest of the two commonest cases, so the rule fired again while
the server was serving the error page, and the server gave up and served its own.

The site was fixed by blocking only the **extensionless** error URL: the ErrorDocument subrequest
asks for the `.html`, which that rule can no longer match. No server variable is involved, so it
behaves the same on both servers.

**Why it was silent, and this is the part that belongs to the system.** EST-03 has two halves. The
candidate measures the *content* of `404.html`, and that was fine. Whether the host *serves* it
with a 404 was deferred to "after the upload" — and after the upload the door printed that G11 had
answered the candidate-only checks, EST-03 among them. **G11 compared the md5 of every file in the
tree and never requested a URL that does not exist.** The sentence was a claim nobody measured.

**Caught by:** G11 now asks the host. It requests two invented URLs — extensionless and `.html`,
because on our sites they walk different rules — and each must answer **404 by itself** with the
tree's `404.html`: byte for byte, or at least carrying its `<title>`. A 200 is a soft 404, a 3xx
is a chain, and any other body is the server's page. A tree without `404.html` says NOT VERIFIED.
`gates/receipt-tests/tests-404-host.sh` drives a test server through the three behaviours; it was
seen red against the previous G11 (**10 failures**, the two that matter being "generic page: exit
0" and "soft 404: exit 0") and green after (**16 · 0**). And the door no longer lists what G11
answered from a fixed list: it reads it from what G11 printed in that run.

**The cheap signal:** `curl -s https://site/any-invented-path | wc -c`. If your `404.html` weighs
ten thousand bytes and that says eight hundred, the visitor is not seeing yours.

> **A test server is a stand-in for the host, not the host.** A bank that passes on the stand-in
> proves the rules; only production proves the server that runs them. Anything whose behaviour
> depends on the server — error handling above all — gets asked of production, after every upload.

## §83 · A page-type profile that failed its own four references

The careers type (`empleo`, [`09 §2.14`](../../blueprint/09-page-types.md)) was derived from four
reference pages, and its layout profile got `hero:true`, justified in a comment as *"three of the
four references put the first action there"*. The justification was true. It was also irrelevant:
`hero:true` switches on a rule that requires a **conversion mechanism** in the first screen, and
**none of the four references takes applications on the page** — their first action is a link to
the openings, to a local office, or to an external system. The first real careers page measured
failed *"HERO · no action is a conversion mechanism"* for doing exactly what the references do.

**Why:** the flag was chosen by *where* the action is, while the rule it switches on also judges
*what kind* of action it is.

The obvious fix, `hero:false`, is wrong too: it also switches off the two things §2.14 does ask
for — an action in the first screen, and at most one primary. The fix is a third value,
`hero:'accion'`, that keeps those two and drops the conversion requirement.

**Caught by:** the structure-gate battery, FRONTERA 6 (`gates/structure-gate-tests/battery.sh`),
four cases so that "stopped accusing" cannot be "stopped looking": a link-only hero passes as a
careers page · two equal primaries still fail · no action in the first screen still fails · the
same page measured as a service page still requires conversion. The first case was seen red
against the previous gate.

**The cheap signal:** before giving a page type a profile, run the gate over its reference pages,
or a faithful fixture of them. **A profile its own references fail is not a standard.**
