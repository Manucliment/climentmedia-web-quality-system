## §90 · Git Bash's `grep -iF` aborts, and `||` read the crash as "not found"

The door's new decision checks that the `--aun-asi` reason names every red browser gate. The first
version did it like this:

```bash
printf '%s' "$AUN_ASI" | grep -qiF -- "$gate" || faltan="$faltan $gate"
```

On Git Bash for Windows that `grep` **aborts**. The shell prints `Aborted` and the exit status is
134, measured with its GNU grep 3.0 under `C.UTF-8`. It needs `-i` and `-F` together: `-F` alone,
`-i` alone and `-iE` all return 0 on the same input. The `||` cannot tell a crash from "no match",
so every gate counted as not named. A reason that named every red gate was
rejected with "the reason does not name: mobile-gate structure-gate".

**It failed closed, which is the only reason it was cheap.** The same pattern written the other way
round would have failed open: `grep -qiF … && named=1` treats the crash as not named too, and the
same pattern guarding a forbidden word would let it through.

**Why it was not seen at once.** The `Aborted` line goes to stderr, in the middle of the door's own
output, and reads like noise. The bench saw it because it compares the exit code and the expected
sentence for each case.

**The fix.** The reason is lowercased once with `tr '[:upper:]' '[:lower:]'` and compared with
`case "$motivo" in *"$gate"*)`. That needs no `grep` at all. The other two tests in the same
function use `grep -qE` on the lowercased text, with no `-i`. A comment at the spot says why.

**The cheap signal.** An `Aborted`, `Segmentation fault` or `Killed` line next to a pipe. A pipe
with `||` or `&&` after it gives every way of failing the same answer as "no".

**Caught by:** `deploy-tests/tests.sh`, block `nav_decide`. Its cases «nombra los dos: sube y deja la
nota» and «nombrar el navegador sin decir que contesta: sube» go red if the comparison crashes
again. They expect exit 0 and the note, and a crashing comparison gives exit 1 and no note.
