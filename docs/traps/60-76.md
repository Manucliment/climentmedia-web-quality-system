## §60 · A rule written FOUR times: 363 failures on a correct site

The site auditor resolved "URL → file on disk" in **four different places**, each written by hand.
None of them knew the **flat-file** convention (`/about` → `about.html`), which is what two of the
sites use.

The first time it was run against one of them: **363 FAILURES**, of which 310 were "broken link"
pointing at pages that exist. With the four copies unified into one resolver and its inverse:
**4**, and all 4 real.

> **What gave it away was not reading the code: it was the number.** 363 failures on a site that
> had been serving for months. *If the sweep says everything is broken at once, the broken thing is
> the sweep.*

> **And the part you do not see:** the configuration file **already declared** each site's
> convention. The data existed and the auditor did not know about it. **Two places, one truth, and
> the one making the decision was the one without it.**

**Caught by:** the auditor's battery, 24 cases exercising **both** URL conventions against the same
resolver. While the rule was written four times there was nothing to test.

## §61 · A check that only emits a line when it FAILS cannot distinguish "fixed" from "did not run"

One measurement check had no pass branch. When the defect is fixed, **the line disappears** — exactly
as if the block had not run. I once accepted a legal fix as done and could only confirm it **by
luck**: a neighbouring check emitted PASS from the same else-branch, so I knew it had run.

→ **Every check emits a line ALWAYS, pass or fail. A gap is not information.**

**Caught by:** in the specific case that exposed it, three cases over a no-form fixture that require
NOT VERIFIED rather than absence. In general, **nobody**: 12 checks still only speak when they find
something. See §65, which is the repeat offence and cost three checks never being measured at all.

## §62 · Two instruments sabotaging each other: the compliance matrix destroyed deploy receipts

The compliance matrix called the master gate with `--repo` and **without** `--no-receipt`. Since it
measures PRODUCTION, every matrix run **overwrote the receipt on all 5 sites** with a production one
— and then the door stopped at step 1 with "INVALID RECEIPT · measured against PRODUCTION".

Measured: **4 of the 5 receipts** changed at the same time as the run. Nobody had connected it,
because **both programs work perfectly on their own.**

→ When you wire an instrument that calls another, look at **what the inner one writes**, not only at
what it returns.

**Caught by:** nobody. It would need a case that runs the matrix over a repo with a receipt and
asserts the file is byte-for-byte unchanged. Today the only defence is that the call carries the
flag, and nothing checks that.

## §63 · Perl's substitution right-hand side interpolates: an array sigil vanished and the gate looked blind

A battery case wrote `{"@type":"Article"}` with a one-line Perl substitution. The right-hand side of
`s{}{}` is **double-quoted**, so Perl interpolated `@type` as an empty array and the file ended up
with `{"":"Article"}`.

The case came out **GREEN**, and the natural reading was "the check is blind". It was not: **the
fixture was broken.** The "did the mutation change the file?" assertion did not catch it, because the
file **did** change — just wrongly.

→ A fixture with a sigil inside is built with `printf` and injected. And faced with a case that comes
out green: **look at the fixture before accusing the gate.**

**Caught by:** nobody — a method trap.

## §64 · A control that passes for the wrong reason

Testing a gate index in the red, the command returned `EXIT=1` and I was about to accept it. The 1

→ **A positive control has to NAME what it detected**, not just return a code. If you only look at

**Caught by:** nobody — a method trap.

## §65 · A check that is not emitted reads as covered

The master gate had three form checks that **did not appear in the report**: no PASS, no FAIL, no NOT
VERIFIED. They vanished. The cause was one line:

```perl
$formsrc = fetch($contact_url)->{body} // $h if $contact_url && ...
```

That fallback substituted the contact page with the **home page** — which has no form — as soon as
the contact flag was empty, which is its default. And **the deploy door has never passed it**: the
command it prints does not carry it. Result: those three were never measured in any receipt, and they
are the ones covering **the site's only conversion point.**

Measured on a live site: **with** the flag, 2 failures; **without** it, 1 — and not a word that
anything was missing. Another site deployed the same way: it has a form and its receipt does not
mention those three once.

**It is not the same as a NOT VERIFIED.** That one is counted, printed, and carries its reason: it
leaves a hole to look at. **An absent check leaves nothing.**

→ **No path may end without emitting.** If the data to measure is missing, you emit NOT VERIFIED with
the reason. **A fallback that substitutes the source with another plausible one is the same family as
a shared cache: it raises no error, it returns data about something else.**

→ And the question that exposes it is the usual one: **what would have to happen for this to go red?**
If the answer depends on somebody remembering an optional flag, it is not tested. Here the answer did
not even exist: there was no way to make it red, because the check never got to speak.

**Caught by:** three cases over a no-form fixture that require NOT VERIFIED — and not absence — when
there is no `<form>` in the tree.

## §66 · An FAQ with its questions in paragraphs is a wall, and the good mould avoided it by itself

Adding an objections block to 8 guides, three of them went from green to red in the density gate with
a failure I had never seen: **"1 block over one screen WITH NO STOP."**

The cause is one line. The gate defines a stop as `h1..h6, li, img, picture, figure, svg, video, tr,
dt, button, summary, label, input, select, textarea` — and says explicitly that **a paragraph is not a
stop.** One FAQ mould emitted question and answer as two paragraphs inside a wrapper: four questions
in a row are eight paragraphs with not one resting point, which is exactly the wall of prose this gate
exists to catch. **And nobody noticed because until that day the FAQs were short.**

→ **An FAQ question is a subheading, not a paragraph.** A heading element fixes it, is semantically
correct, and does not change a pixel if the CSS already sets size, weight and margin on the class —
which is what you check BEFORE touching it, because a heading rule with a size token does exist and
would lose to the class on specificity, but letter-spacing would not. 221 questions in 50 files, and
afterwards: **zero heading-order skips across 29 pages.**

→ **The other four sites did not have the defect**, and not by luck: they use `<details>/<summary>`,
and a summary **is** on the stop list. **The mould in the repertoire already solved it; the one that
skipped it was the site where the standard lives.** Same pattern as the alt-text rule.

**Caught by:** the density battery — a case with 5 paragraph pairs that must FAIL, and its twin with
the same text in headings that must PASS.

## §67 · A gate that counts calls to action by selector approves invisible buttons

I added six calls to action to fix the CTA-less stretches the density gate was flagging. I measured
again: **PASS.** All six buttons were in the DOM, measured 426×53 px, and the gate counted them.

**None of them was visible.** A prose rule with higher specificity than the button class meant a
button inside a paragraph received the accent colour — **on top of the button's own accent
gradient**: the same orange on the same orange. Contrast about 1:1, and underlined. Fourteen like that
across the site, eight of them predating that day.

→ **The vicious circle is the thing to see:** I was fixing a conversion problem *by adding buttons
nobody can click*, and measuring with an instrument that confirmed it was already solved.
**A gate that checks presence can never contradict another that checks presence.**

→ **What exposed it was comparing MY button with one that already existed**, same class, and seeing
two different colours. Not a screenshot: computed styles. And the background has to come from
`backgroundImage`, not `backgroundColor` — in a gradient the background colour is transparent and a
careless meter concludes "transparent background, contrast fine."

→ The fix is done **by class, not by location**: `:not([class*="btn"])` in the prose rule. "Do not put
buttons inside paragraphs" does not survive the next generator that emits its afterword as a
paragraph.

→ And the sweep to find where else it applies **lied first**: it said another site had the same rule,
and it was in the archived copy of that site's old CSS, not ours. **Opening the file cost ten
seconds.**

**Caught by:** nobody, automatically. One check declares **NOT VERIFIED** for exactly this family
("rules whose real background cannot be known by reading the stylesheet": 388 rules on one site),
which is honest and is not a pass. It is measured in the browser on the candidate, one button at a
time: the computed colour against the first colour stop of the computed background image, and
contrast below 4.5:1 is a failure.

## §68 · Two gates measure the same thing with different rules, and one fell behind

One home page came out **PASS** in the density gate at three widths, and **FAIL** in the master gate's
equivalent check with the same DOM in front of it. **Both claim to measure "density and calls to
action."**

Read side by side, the thresholds are not alike:

| | master gate's check | the density gate |
|---|---|---|
| tall block | "no block over one screen", over the CONTAINER | over the **UNIT** (§47) |
| long page | "≤6 screens", flat | `6 + (words−400)/80`, scaled |
| stretch with no CTA | whatever the probe hands it | a run of consecutive **blocks** with no CTA |

The first two were changed by §47 and the word-counting rule **in the JavaScript and not in the
Perl.** Measured effect: the page gives 9.0 screens at 390 against a computed limit of 10.9 → PASS;
the other check fails it for exceeding 6. And with the container rule it would fail **10 of the 19
moulds in the repertoire** — which is literally the contradiction §47 exists to have closed.

→ **And the third is worse, because it is one word meaning two things.** The probe emits a gap measured
in pixels between consecutive calls to action, trailing gap included. The check compares it against a
threshold worded "≤2.5 screens with no CTA", which in the other gate is a run of blocks. Measured on
the same page: **2.99 vs 1.3.** It is not that one is wrong: **they are called the same and they are
not the same thing.**

→ Same disease as the anatomy table written three times (§44) and the four-times-written resolver
(§60): **two copies of a rule do not diverge "if" somebody gets careless; they diverge.** The only
question was when.

**Caught by:** nobody. You see it by putting both instruments on the SAME page and comparing verdicts,
which is how it came out. The fix is a single source. Until then, **the good verdict for layout is the
density gate's**, which is the one with a battery and the one the door runs before uploading.

## §69 · Declaring a font is not loading it, and `ch` measures the one that actually paints

One site declared a font stack from day one and **had neither an `@font-face` nor a font file.**
Asking for a font does not fetch it: if the visitor does not have it installed — and almost nobody has
that one — the browser falls to the next in the list. Measured: **three different faces across three
operating systems.** *There was not one typeface: there were three, and none was the chosen one.*

**How it surfaced, which is the interesting part: through a number about something else.**
`max-width: 65ch` resolved to 36.1 em and gave **83 CPL**, above the hard ceiling of 80. The
measurements table says 36.2 em is 66–77 CPL. The width matched and the CPL did not.

→ **`1ch` is the width of the "0" glyph OF THE FONT THAT RENDERS.** 0.50 em in one face, 0.555 in
another. I was calculating with the metrics of a font that never arrived. **The rule is written in
`em`**, which depends only on the font size.

→ **The cheap signal, and it costs one line:** an empty `document.fonts` in production means the site
has no font of its own, whatever the CSS says. The confirmation is measuring the "0" glyph with the
declared stack and comparing it against the font you think you have.

→ **And the way to ruin it while "fixing" it: the `@font-face` RANGE.** Another site serves the same
variable font file declaring `font-weight: 400 700`. The file is variable **100–900** — measured with
the fonts loaded and synthesis disabled, six weights give increasing widths. Copying that declaration
would have left **nine** uses of weight 800 **synthesised**: fake bold, which looks worse than the
system font it replaced. **An `@font-face` can under-declare its file, and nobody notices because the
browser fakes the rest.**

→ **And not every file is equivalent:** one 26 KB variable file gives **erratic** widths, narrower at
800 than at 600. Same name, same format, different behaviour.

→ **Before believing the change broke the site:** switching the font on, 11 of 12 pages came out FAIL
in the layout gate. Measuring the same 12 **with and without** the font in the same iframe, the
verdicts are **identical** and the CPL is equal or **one lower** with it. The failures pre-existed;
what had happened is that the gate **had only ever been run on the home page**, because that is the
only page the door measures.

**Caught by:** nobody automatically. The check is two lines in the browser against production.

## §70 · An anchor assuming an HTML entity where the file has the LITERAL character matches zero, and `sed` hides it from you

Converting a home page, two different substitutions on the same day died with *"appears 0 times"*:

```
<title>Brand &mdash; AI Advertising…   ← what I wrote in the anchor
<title>Brand — AI Advertising…         ← what was in the file
```

The file mixes both forms: entities in some places and the **literal character** in others, depending
who wrote that line. There is no way to tell by looking at the page: **they render identically.**

→ **And the obvious diagnostic LIES.** Piping a line through `sed` and then through `cat -A` printed
no unusual bytes and no carriage return. Both were there: **`sed` normalises as it reads**, so a
`cat -A` after a `sed` does not describe the file, it describes what sed handed it. That is why the
second attempt failed again with a two-line anchor: **the file was CRLF and the pipeline had hidden
it.**

→ **The only witness is the raw bytes**, and it costs one line:

```bash
grep -o '<title>[^<]*</title>' file.html | cat -A        # grep does not normalise
perl -0777 -ne 'if(/ANCHOR(.{0,30})/s){$x=$1;$x=~s/([^\x20-\x7e])/sprintf("[%02x]",ord($1))/ge;print"«$x»\n"}' f
```

→ **And the literal cannot be typed**: some transports decode escapes, so you build it in execution —
`my $EM = "\xe2\x80\x94";`.

→ **The rule, which is the cheap one:** an anchor of more than one line is a bet on the line break
**and** on the line ending. **One-line anchors**, checked against the file before writing them.

**Caught by:** nobody automatically — but the pattern **is covered by the discipline of "a substitution
must assert how many it MADE"**: all three failures surfaced immediately because the script checks the
count **before** writing and dies without touching the file. Without that assertion, all three would
have been silent zero-line substitutions with the program reporting success.

## §71 · A line-length measure started from the node, not from the line: a 73-character paragraph returned **2**

A layout gate warned *"median line length 43 characters across 5 reading paragraphs, outside the
45–90 range"* on a page whose paragraphs measure 544–620 px and read perfectly.

**The cause.** The measure took *the first loose text node over 60 characters* in the paragraph and
measured from its first character to the line break. If the paragraph starts with an inline element —
bold, a link, emphasis — **that node starts mid-line**, and what gets measured is the remaining stub,
not a line.

Measured with a probe that replicated the function and added the datum the gate does not print,
*where in the line the chosen node starts*:

| Paragraph | Node starts | measured | real width |
|---|---|---|---|
| hero subtitle (620 px) | x=205 | **43** | ~66 |
| section subtitle (544 px) | x=475 | **2** | ~73 |
| three starting at x=0 | x=0 | 68 · 39 · 75 | correct |

Sorted: 2, 39, 43, 68, 75 → median **43**, exactly what was reported. **A line length of 2 is not a
line length**, and that single figure was enough to discard the measurement without arguing about the
rest.

→ **The false positive is NOT symmetric: it only drags the median down, never up.** It always accuses
of the same thing — "line too short" — so the bias runs in a fixed direction, and anybody reading it
often enough will end up accepting that accusation on pages that are fine.

→ **The fix was not surrendering to a canvas estimate, it was measuring properly**: advance the index
to the first character that STARTS a line (x within 4 px of the paragraph's content edge) and measure
from there. If the node never starts a line, return null and fall back to the estimate, which already
existed.

→ **The red case, and why it is a good one:** a copy of a passing fixture with the first words of each
paragraph wrapped in bold. **Same visible text, checked character by character; same width; same
layout.** Before: FAIL, median 17. After: PASS, 65. And the control without the bold stays at **67**:
two apart, which is what a bold weight costs. *If it had come out 65 and 65 exactly, the fix would be
measuring a constant instead of the world.*

**Caught by:** the layout gate's battery, the bold-prefix case.

## §72 · A replacer FUNCTION does not expand `$1`: returning it from inside writes it LITERALLY

A migration generator had a helper that counted substitutions, and therefore **always** passed a
function to `String.replace`:

```js
const out = txt.replace(re, (...a) => { n++; return typeof rep === 'function' ? rep(...a) : rep; });
```

With `rep` = `'$1\n  <base href="/shop/">'` that writes **a literal `$1`**. The `$n` references are
only expanded by `replace` when the second argument **is a string**; inside a function the returned
value is inserted verbatim.

Result across **12 pages**: the viewport meta tag and a social meta tag **gone**, replaced by the
string `$1`. **A site with no viewport tag is not a detail: it is the entire mobile layout.**

→ **And what matters: the generator's self-check was GREEN.** It looked at what I had gone to add —
headings, canonical, old domain, sealing, loose links — and none of it looked at **what had been lost
along the way.** It is *"a PRESENCE gate approves the invisible"* again: you check that what was added
is there and nobody checks that what was already there still is. **Reading the output found it, not
the program.**

→ **The fix, and the shape to copy** — one pass that only counts, and the real substitution by the
appropriate route:

```js
function sub(txt, re, rep) {
  let n = 0;
  txt.replace(re, () => { n++; return ''; });        // pass that only COUNTS
  const out = typeof rep === 'function'
    ? txt.replace(re, (...a) => rep(...a))
    : txt.replace(re, rep);                          // string: here `$1` IS expanded
  return [out, n];
}
```

→ **And the new check was born BLIND.** I wrote it as `/$[0-9]/`, where `$` is *end of string*: it
never matches. Green forever. It was caught by running it against the damaged output still on disk —
`/$[0-9]/` green, `/\$[0-9]/` **red**. The usual question: *what would have to happen for this to go
red?*, and answering it **by executing it**, not by reading it.

**Caught by:** the generator's own two checks — "a literal `$n` remains" and "the viewport tag was
lost" — both tested against the broken output before being accepted.

## §73 · A CDN that rewrites images turns the served-equals-measured check into 12 false reds per deploy

First run of the served-equals-measured check behind a hosting CDN: **49 files identical and 12
DIFFERENT**, with the banner *"PRODUCTION IS NOT SERVING WHAT WAS MEASURED"*. **All 12 were images and
none was uploaded wrongly.**

Measured file by file, the CDN does not do one thing, it does two:

| | |
|---|---|
| **PNG** | it **recompresses**: same dimensions, adds a chunk, rewrites the data. 26,099 bytes in the repo → **27,280** served |
| **JPEG** | it **resizes**: 1726×911 → **1600×844** |
| **if you accept webp** | it returns something else entirely: **13,768 bytes** |

→ **What was tried before giving up, because "you can't" has to be tested:** a no-transform cache
directive, a wildcard accept header, no user agent, a curl user agent, and a cache buster. **All five
return the transformed version.** And on top of that the CDN **strips the modification date and entity
tag from images** — the CSS keeps them — so there is not even a freshness signal to say "this is the
new one".

→ **Why it matters more than it looks:** a red that appears on **every** deploy and that nobody can fix
does not protect anything. **It teaches people to ignore the gate**, and the day the red is real nobody
looks any more.

→ **The fix, and the shape to copy.** It is not "skip images": that blinds the gate for exactly the case
that matters. The exception requires **both things** — that something demonstrably transforms **and**
that what is served is still a valid image — and the result **is not an OK, it is a NOT VERIFIED** with
the hole stated:

```
  transformed by a CDN, NOT verified: 12
  CDN-NOT-VERIFIED  assets/og/home.png · Server: hcdn · PNG 1200x630 · 27280 bytes · md5 not checkable
  WHAT YOU DO NOT SEE HERE: an image that was never uploaded whose old version
  is still being served. That is answered by the md5 against disk over SSH.
```

→ **And it can still go red**, which is the only thing that needed protecting: with no CDN in front, an
image md5 that does not match **is still a FAIL**; if the CDN returns HTML or an anti-bot challenge,
**FAIL**; and stylesheets, scripts and pages keep full coverage. Also, if **everything** looked at were
transformed images the verdict is `COVERAGE`, not `PASS`: not a single file would have been verified.

**Caught by:** a dedicated control file — **14 controls, 7 of them negative** — hung off the runner. It
extracts the CDN-detection function from the real receipt program, not a copy. Also tested against a
deliberately weakened version: the controls catch it with **2 failures.**

## §74 · An honesty guard wired to ONE value declares "this is not a result" for the only thing that sees the defect

A mobile gate had **`matches: vw === 390`** written in it. That field exists for a good and
already-written reason: **on Windows, Chrome clamps the window width to about 500 px**, so a measurement
whose `innerWidth` is not the one requested **is rubbish, not a result.** But it was compared against a
**constant**, not against what was REQUESTED.

Consequence, measured on a live site: at **360 px** — a very common Android width — a phone call to
action is **covered** by the cookie banner, and after accepting, by a popup. The gate saw it perfectly
and said so… underneath a `matches:false` that means "this does not count". **At 390 nothing fails.**
Full sweep: **16/16 PASS at 390 · 7 of 12 pages with a CTA FAIL at 360.**

> **An honesty control that only accepts one value does not check honesty: it checks that value.** And
> it fails in the worst direction of all: not a false red — which gets argued about — but a
> **non-result**, which nobody argues about and everybody discards.

And the human half, which is the usual one: the defect had been declared non-existent with a **24/24
PASS** measured **only at 390**, with "at 390 and 360" written on the card. **Measuring a subset and
reporting the whole — the bias always runs towards optimism.**

**The fix, and the detail that makes it testable:** the runner now injects the requested width and the
gate compares against it. It goes in as a **default** (`Object.assign({requestedWidth: aw}, userCfg)`),
**not as an override**: if it cannot be overridden from outside, **the guard cannot be made to go red**,
and a guard that cannot be made to go red is not tested.

**What to look for in any other gate:** every field like `matches`, `isValid`, `expected`, `suspicious`.
If its definition has a **literal constant** where the requested parameter should be, it is already
silencing something.

**Caught by:** the mobile gate's battery — a section with **3 cases**, one of them NEGATIVE: a case that
requests 390 and declares 400, and **requires `matches:false`**. The other two pin 390 and 360 to true —
the latter is literally the case that used to be impossible.

> Writing them also surfaced a latent bug in the battery itself: the config was passed over `ssh` in
> double quotes, which the remote shell eats, so the JSON arrived broken and the case returned no data.
> **No case passed a config, which is why it had sat there unseen.**

## §75 · `if (r.cssRules)` no longer distinguishes a group rule: CSS Nesting gave it to ALL of them

Walking the CSSOM to check whether a rule is genuinely parsed, the long-standing pattern was:

```js
for (const r of sheet.cssRules) {
  if (r.cssRules) { walk(r.cssRules); continue; }   // media, supports, keyframes
  inspect(r.selectorText);                          // ordinary rule
}
```

**Since Chrome supports CSS Nesting, an ordinary style rule ALSO exposes `cssRules`** — an empty list,
which is **truthy**. Measured: the property is present, its length is 0, and the coercion is true.
Result: the `continue` fires on **every** rule, **none** gets checked, and the walk finishes **with no
error and no results.**

> It came out saying **"5 of 5 new rules are NOT parsed"** on a stylesheet where all five were and were
> working. What gave it away was that the gate's measurements contradicted the probe. **If the sweep
> says everything is broken at once, the broken thing is the sweep** — again.

**How to do it properly:** distinguish by type, not by the presence of a property.

```js
if (r.constructor.name === 'CSSMediaRule' || r.conditionText !== undefined) { ... }
// or: r instanceof CSSMediaRule · or: r.type === CSSRule.MEDIA_RULE
```

And for a census, an **indexed** loop grouping by constructor name: it tells you at a glance how many of
each rule type there are, and there you see immediately whether the walk is losing a whole family.

**Caught by:** nobody, on purpose. **No gate in this system walks the CSSOM** — verified with a grep,
zero uses — so there is no live blind spot to protect: this is a trap for the NEXT probe somebody writes,
and that is why it lives here and not in a battery. If a gate ever starts walking rules, this case needs
a fixture.

## §76 · A template literal lost its interpolations and the warning went mute

Found reading the diff just before committing. The line said, literally:

```js
notes.push(`MEASURED AT px when  were requested. Chrome clamps at ` + …);
```

It was missing two `${...}` interpolations. **And a syntax check gave GREEN**, because a template with
no interpolations is perfectly valid JavaScript.

**Why it hurts precisely here:** that warning is the guard for the Chrome clamping problem — *"a
measurement that does not match what was REQUESTED is not a result"*. Without the two numbers **it does
not say what was measured or what was asked for**, so the one message capable of exposing a false
measurement becomes noise nobody reads. The gate kept "warning" and the warning no longer informed
anybody of anything.

**Caught by:** nobody automatically, and **the first sweep I wrote to look for siblings did not catch it
either**: I used a pattern built from the words I imagined, and passed through the genuinely broken line
it **did not match.** The zero it returned was worth nothing. The pattern that DOES work looks for the
signature of the gap, not for words:

```bash
grep -nE '`[^`]*([ ]{2,}|[ ][.,:;])' gates/*.js   # two spaces, or a space before punctuation
```

With that: positive control green on the broken line, and **4 more occurrences, all 4 legitimate.**

> **The lesson is the usual one, and here it bit me inside my own check:** *a sweep with an invented
> pattern measures my hypothesis, not the fact.* **Before trusting a zero, run the pattern against a
> genuinely broken case.** It costs five seconds and it is the difference between having looked and
> believing you looked.
