## §20 · A check that decides with a number that depends on how much you measure

**Caught by:** the master gate's battery — the ratio, **per page and worst case**

Measured on one site, **same site, same binary, same cache**; the only variable is how many
pages enter the sample:

| coverage | third-party bytes | ratio | verdict |
|---|---|---|---|
| 1 page | 152 KB | **56%** | **FAIL** |
| sample of 3 (default) | 152 KB | 46% | PASS |
| all 40 | 152 KB | **8%** | PASS |

**The numerator does not move.** The 152 KB of tag manager are the same in all three. What
grows is the denominator: the union of resources across the sampled pages. So the percentage
**is not a fact about the site, it is a fact about the run** — and widening coverage *switches
the failure off*, which is the one direction a gate cannot afford.

**What makes this trap special: it was already declared.** The check's own header explained it
with its own figures, and the printed evidence shows the sample size next to the percentage so
nobody reads it as a fact about the site. All correct… except that **the `if` does not read the
warning**:

```perl
if ($third > 300*1024 || ($pct > 50 && $third > 100*1024)) {
```

The absolute branch (300 KB) is sound and coverage-independent. The ratio branch **gates on the
number its own comment says not to believe.** A warning in a string protects nothing if the
threshold still looks at the variable.

→ **Proposed fix, not applied:** compute the ratio **per page** (worst case among those
  measured), not over the union. *"Third parties are 56% of this page's weight"* is a fact about
  the site; *"8% of the union of 40 pages"* is a fact about the sampling.
  Changing it **would make a real site FAIL** for a real defect, so it is a decision, not a
  silent fix.
→ It generalises: **if a threshold looks at a variable that depends on the instrument,
  documenting it is not enough — you have to take the dependency out of the threshold.**

### What was RULED OUT in the same pass, and also has to be written down

Two other things were suspected. Measured, they are not real:

- **"Findings are not deterministic between runs."** **False: the gate is deterministic.** Three
  runs with the same cache → identical. Two runs each with a fresh cache → identical. Warm
  against cold → identical.
- **"The sample is a lottery of which 3 pages you get."** **False since a earlier fix**: the
  sample is distributed deterministically and always keeps the first page.

**What was actually behind both suspicions is something else, and it is the one that matters:
a finding's FINGERPRINT depends on coverage.** Same defect, same frozen bytes, same visible
evidence line:

```
sample 1   ->  FINGERPRINT EVS=a315120e
sample 3   ->  FINGERPRINT EVS=a315120e
sample 12  ->  FINGERPRINT EV=d623b1aa      <- different prefix AND different hash
```

And **it is deliberate** — it is written in the fingerprint function: *it ties the acceptance to
THAT scope; if tomorrow you measure the whole site, the fingerprint changes and you have to
decide again with the better data.* Practical consequence to know before signing anything:

> **An acceptance is tied to the coverage it was signed with.** Changing the URL cap or the
> sample size leaves it unmatched, the FAIL counts again and the deploy blocks. **It fails on
> the safe side** — nobody gets silenced without knowing — but it explains "this matched
> yesterday" with nobody having touched the site.

> On method: the non-determinism suspicion came from comparing two runs that **did not have the
> same coverage.** Before calling something non-deterministic, fix ALL the flags and look again.

## §21 · A rule demanded that the home page link to HALF THE SITE, and it was arithmetic

**Caught by:** the crawler's battery (hub rule on a flat site): 5 cases, 2 expecting FAIL

The linking gate derived each page's parent **by stripping the last path segment**. On a **flat**
site — every URL at one level, which is how two of ours are built — the parent of all 28 pages
comes out as `/`, and the rule ended up requiring that **the home page link to all 28**: the 11
blog posts and the legal notice included.

That **collides head-on** with the rule capping the menu (≤15 links per page) and turns the home
into a sitemap. And it is not a rare case: on one site it had been accusing since it was written
— *"does not link to 18 of its 28 children"*, then 15 — with not one linking defect behind that
number.

**The path does not tell you what hangs off what when there is no hierarchy IN the path.** What
does cover it is the rule requiring each page to have a content inbound link, and the zero-orphans
rule, both checked right alongside.

**Fix:** the root answers only for the children that **are hubs themselves** — the home page has
to link to each **section**, not to each page. On a flat site there are no sections, and then the
rule **says so**:

```
PASS   R5 the hub links to its children   no hierarchy in the URLs: nothing to check (R3 and R4 cover it)
```

> A bare `PASS` reads as "hubs verified". If there were none to look at, that has to be written,
> or the green line lies by omission — the same disease as §18.

**And here was the method risk, which is the part to remember:** relaxing a rule so my site
passes is exactly the failure this gate exists to prevent. So the fix arrived with **five cases —
the gate's first — and two of them expect FAIL**: an incomplete section, and a home page that
misses a section. If relaxing had turned those green, the fix was a fudge. **Both flat cases were
seen red before the rule was touched.**

## §22 · A one-line replace over a template file put rubbish into 12 live pages

**Caught by:** nobody · hard rule: a script that deletes something checks what it LEAVES, not
what it removes

Removing a `data-event="…"` attribute from a generator — a check had flagged it as emitted with
no reader, and was right — the script searched for `\s+data-event="[^"]*"`. But **in a PowerShell
string, quotes are written doubled**: the file said `data-event=""whatsapp_click""`. The pattern
matched ` data-event=""` with `[^"]*` **empty**, and left the inside loose:

```html
<a class="btn" href="https://wa.me/…?text=…"whatsapp_click" data-loc="stair" …>
```

**And the script passed itself**: its check was *"no `data-event` remains"*, and none did. It
verified **the absence of what it removed, not the integrity of what it left.** Twelve pages
deployed like that — the link still worked, so neither the browser nor any check said a word —
and it was found two days later reading the home page's HTML for something else.

→ **Rule, and it is not "be careful":** a script that deletes an attribute **checks the result,
  not the disappearance.** At minimum: that the count of well-formed anchors did not change, or
  run the output through a parser. And before writing the pattern, **open the file and see how
  it writes quotes** — two lines of `sed -n '406p'` would have been enough.

## §23 · A rule counted repetitions and claimed "it links half the site"

**Caught by:** the crawler's battery (menu rule counts occurrences): 3 cases

Running five sites through the gate, the menu rule **failed on 3 of 4 measurable ones.** That
shape — several things broken at once — is the one that forces you to suspect the instrument
before the site, so I counted by hand.

The crawler counted link **occurrences**, not distinct destinations. A footer with six anchors
to `/services#a`, `#b`, `#c`… sums to **six** and points at **one** page. And the hard condition
compared those occurrences against the number of **pages**:

```perl
if ($maxnav > $lim && $maxnav >= 0.5*$N)   # apples against oranges
```

| Site | Occurrences | Unique destinations | Real % of site | Old verdict → new |
|---|---|---|---|---|
| Site A | 29 | 10 of 16 | **62%** | FAIL → FAIL (correct) |
| our own | 35 | 26 of 44 | **59%** | FAIL → FAIL (correct) |
| Site D | 25 | **10 of 40** | **25%** | **FAIL → WARN** |
| Site C | 15 | 10 of 29 | 34% | PASS → PASS |

**One site was falsely accused** of its menu linking half the site when it links a quarter. The
other two were true and still are.

**No threshold was touched** — the only thing that changes is **what** gets compared against half
the site. Three cases in the battery, and the false one **was seen red with the old condition**
before the fix was accepted.

> **The lesson, appearing for the second time in a day** (§21 was the other): when a rule prints
> a sentence — *"the menu links half the site"* — you have to check that the number firing it
> measures **that** and not something similar. Both times the failure was in translating the
> statement into the data, not in the threshold.

## §24 · The hand-duplicated menu: you fix the template and the gate does not move

**Caught by:** nobody · the census is manual (`grep -rl '<header class="nav'`). **OPEN**

Fixing the menu rule, I took the generator's menu from 26 distinct destinations down to 16.
**The gate still reported 24 and FAIL.**

The cause: the linking gate reports the **worst case on the site**, and 21 pages of that site —
the home, the three legal pages, a landing page and **the 15 guides** — carry their own
hand-written copy of the header. The generator does not touch them, so they still had the old
menu.

**What to take from this is not the number, it is the pattern:**

> **A gate that does not move after a correct fix is telling you there is another source.** It is
> not that the fix is wrong: it is that it does not cover everything. Before touching the
> threshold or doubting the gate, **census who else produces that same thing.**

And comparing the two versions surfaced what no gate was looking for: **the hand-written menu was
missing the product pricing page.** It was not in the home's menu or in any of the 15 guides, and
it had been like that since they were created. Duplication does not just age: **it drops whatever
gets added later**, and nobody notices because each copy looks reasonable on its own.

### §24-bis · A breadcrumb detector measured the WORD, not the fact

In the same sweep, one page was accused and was impossible to fix: a documentation page
**explains** which schema each page type carries and shows the escaped example. The detector was
a plain match for the schema name over the whole HTML, so it counted the page as emitting a
schema it does not emit — and then demanded a breadcrumb from it forever.

Now it searches **only inside the JSON-LD script blocks.** Five cases, three expecting zero: the
escaped mention, the word in a documentation table, and a JSON-LD that is not a breadcrumb.
**All three were seen red with the old detector.**

It is the third time in two days that the same family shows up wearing different clothes:
**a regular expression over HTML measuring my hypothesis instead of the fact.**

### §24-ter · A new component takes its CSS to the sheet loaded by WHOEVER uses it

Taking the breadcrumb to three legal pages, the component lived in one stylesheet — and **those
three only load the other one.** They would have shipped with bullets and orange links: a class
with no CSS. It is checked with one line before writing the component:

```bash
for f in privacy.html terms.html; do grep -o 'href="[^"]*\.css"' $f; done
```

And after moving it, it clashed **twice more**, both with page-level rules that tie or win on
specificity and come later: orange links, and a list at **82 px tall instead of 23.**

→ **You exclude it in the WIDE rule (`:not(.crumbs li)`), you do not raise the component's
  specificity.** Raising it wins this time and loses the next: the next person to add a navigation
  component inside those wrappers overrides it again, and *that* no gate detects.

> And the method, which is what makes this visible: **all three clashes came from computed
> styles, none from looking at a screenshot** — and when the browser harness returned
> `innerWidth: 0`, the geometry measurements from that pass **were not used.** A height of 73 px
> measured in a zero-width viewport is neither a defect nor an exoneration: it is a
> non-measurement.

## §25 · The door promised to leave a record, and it was an `echo`

**Caught by:** the door battery: 9 cases

Auditing the process itself surfaced two things that explain "a new bug appears every day" better
than any site defect:

**One · of the six gates in this system, the door invoked ONE.** Only the receipt. The others were
printed as advice. I ran them by hand after each deploy — and **what depends on somebody
remembering fails the day they do not.**

**Two · the "ship anyway" flag was not saved anywhere.** The script promises three times that
*"it stays in the history with your reason next to it"*, and all it did was `echo`. **Measured:**
the history file held **621 actions — 467 QA + 153 served-checks — and ZERO notes.** The
mechanism already existed; nobody called it.

That same day I signed **three deploys** naming, one by one, the 11 checks that had not been
measured. All three reasons were printed and lost.

> **What to take from it:** the damage of signing off a hole is not signing it once — it is
> signing **the same one** many times with nobody able to see it. **A record that does not keep
> the reason turns a repeated decision into a habit.**

**Fixed:** the door now records the flag with the count and the exact list of unmeasured ids,
**only on a real upload** — in a dry run nothing has happened worth recording. And a new step
crawls what has just been served and runs the linking gate. **It goes after uploading on purpose**
(before, it would measure the old site) and **it does not block**: it is already uploaded, and the
gate exits non-zero also when it CANNOT measure, so wired as a blocker one site could never deploy
again. What it does is **get recorded.**

> **How they were seen red, which is the part that matters:** by sabotaging the record function so
> it **said** it recorded and wrote nothing. With that, the assertion *"it says it recorded"* stays
> **green** and only the two that check the history fall. If the test had been written against the
> message, it would have passed with the defect alive — which is exactly how this defect survived.

## §26 · Ten test batteries and nowhere to run them from

**Caught by:** the test runner — one command, every battery, one number

The system had **10 test batteries spread across 5 folders and no master runner.** Each was
launched by hand, when somebody remembered it existed. The safety net was written and
**unplugged.**

The symptom, measured the same day: touching the deploy script, I ran the door's battery and
**none of the other nine.**

### §26-a · A test had been red for a long time and nobody knew

One battery expected a hook to **block** a particular script. The hook has a **deliberate, narrow
exception** — authorised — that reads the script from disk and only lets it through if its
destination is the assets folder and **all** its files are images from a known output directory.
The test was written before the exception and nobody updated it. **A permanent red nobody looks at
is the same as having no test.**

### §26-b · And splitting that test in two surfaced a real hole

An exception with no negative case is a hole nobody looks at: what you have to test is not that it
**passes**, it is that **only that passes.** Writing the negative:

> **The exception's entry condition was the script's NAME**, and the comment directly above it
> said literally the opposite — *"the exception is not the script's name: it is what the script
> DOES"*. It was enough for the script's name to appear **anywhere** in the command: the hook
> always read one fixed copy, saw it was narrow, and let through **whatever command it was.** A
> file with the same name in another repo, whose contents nobody has read, walked straight in.

Fixed: the command has to be **exactly** that script's invocation, in its documented relative form
or its canonical path, and nothing else — which also means nothing can be chained after it.

> **The lesson, which is the day's lesson in other clothes:** the statement and the mechanism have
> to measure the same thing. Here the comment described the correct mechanism and the code did a
> different one, and had done since it was written.

> And one about the runner itself: the first version **could not read** the hook battery's count —
> it has a different format — and printed *"I could not read its count."* Its 24 cases did not
> count towards the total. **A count you cannot read is a zero wearing a pass.** Either you read
> it, or you say so in red.

### §26-c · And within two hours it had paid for itself: changing a rule expires fixtures

Closing §18 — *"a lens that ran and measured nothing is not a PASS"* — the runner produced **7
failures in the door battery and 3 in the master gate's.** None was a defect in the fix: they were
**fixtures written before the rule existed**, with a whole lens NOT VERIFIED because nobody had a
reason to put anything else. Under the new rule the receipt seals them NOT VERIFIED and the door
rejects them at step 1 — so those blocks stopped testing their own subject: they stopped **before**
reaching what they wanted to measure.

**The fixtures were fixed, not the rule.** A fixture with a whole lens in the dark is not the
scenario those tests wanted — that one is tested separately — but an unrealistically thin one that
nobody reviewed.

## §27 · A gate cannot know whether a path is "mine" or "one I am talking about"

**Caught by:** the documentation gate's battery — the case "an internal repo path is NOT checked"

Extending the documentation gate to also check internal repo paths seemed obvious: nobody writes
`_deploy/upload.sh` meaning something else. **Measured over 5 repos and the system itself: 12
accusations, 12 false.**

| Where | What it accused | Why it was false |
|---|---|---|
| two client repos | a secrets file | it is a **pending task**: the file does not exist yet, and it is a secret that must not be in the repo |
| one repo | a path with no backticks **on purpose** | it is inside a **quotation** of what an old document said, describing a past defect |
| **the system itself, 9 times** | spec and deploy paths | **and here is what kills the idea:** this documentation describes **other trees.** Its internal paths are correct in a client repo and do not exist here |

The first two can be bounded — and were, with their cases: an unfinished task and a quotation are
not assertions about the present. **The third cannot.**

> A program cannot distinguish *"a path in this tree"* from *"a path in the tree I am talking
> about"*, and all of a system's documentation is the second.

**The extension was withdrawn entirely**, and this case stays in the battery so nobody adds it
again thinking it is easy.

> And the detail that nearly made me accept a bad exclusion: the quotation **spanned two lines**,
> so the "is it inside quotes" filter did not see it. Instead of making the filter multi-line —
> more surface, more ways to be wrong — the quotation was rewritten without backticks around a
> dead path. **Putting a path that does not exist in `code` makes it look alive**; writing it in
> plain text inside the quotation is more honest for the reader, not just for the gate.

> **And the gate caught me writing this very trap.** The table above quoted the dead path in
> backticks — the error the previous paragraph describes — and the gate flagged it on the next
> run. It is the best proof I can give that the check is worth having: **knowing the rule is not
> enough, and neither is having just written it.** That is why the rule lives in a program.

## §28 · The four documents people follow did not name the door

**Caught by:** the documentation gate's flag check, and the identical block in all four paths

The system has four entry documents — the paths — which are **what somebody reads and follows.**
Measured with a three-second grep:

| | the deploy script | the candidate flag |
|---|---|---|
| Path 1 · new site | **0 mentions** | 0 |
| Path 2 · improve | **0** | 0 |
| Path 3 · add a page | **0** | 0 |
| Path 4 · iterate | **0** | 0 |

**Not one of the four named, even once, the only mandatory door in the process.** And worse: path
1 told you to run the master gate *"over the published site"* and without the candidate flag —
exactly what the top-level document forbids, in the document you read **to build a new site.**

> That is how you end up deploying by hand with every gate green: not by skipping the process, but
> **by following the wrong document.** The top-level document can tell the truth and the outcome be
> identical, because **nobody reads two documents to do one step.**

**Fixed:** all four now carry the **same block**, and their headers say so, so they do not get
edited separately. And the check that was missing is written: the documentation gate compares the
four blocks and fails if any is missing or if they diverge. **A fifth path without it comes out
red.** 5 cases, including the negative that avoids noise: one extra newline is not a divergence.

> Written down because I nearly closed it with *"we must remember to copy it"*, which is literally
> the class of rule that failed in §24 and §25.

## §29 · A gate with 24 checks and zero tests was DEAD

**Caught by:** the spec auditor's battery — 9 cases, and the first is the one that killed it

The coverage counter put a number on the fixture rule, and the worst in the table was the spec
auditor: **0 of 24 checks with a case**, 775 lines. Going to look at it, the first run against a
real repo:

```
$ perl audit-vs-spec.pl --mode migration
Not an ARRAY reference at audit-vs-spec.pl line 181.
```

**The gate was dying.** And dying like that is the worst possible ending: **no verdict, no id, no
line in the receipt.** It does not say "this is wrong" — it says *nothing*, and whoever launched it
is left not knowing whether their site passes.

**The cause is a lesson about specs, not about Perl.** The code dereferenced a key as an array,
assuming `legal` is a **list of pages.** It is, in two repos. In the third, `legal` is a **hash of
settings** — texts, flags. The same key, two meanings, **and neither spec is wrong**: nobody ever
wrote down what shape it had to have.

> It is the "the spec declares the shape, and no program infers it" rule through the back door.
> Here the program inferred it, was right in two repos out of three, and died in the third.

**Fixed:** a collection helper that accepts the list, also accepts the `slug => record` hash — it
is the same collection written differently, and accusing it would be a false positive — and **for
anything else emits NOT VERIFIED with the key's name and its shape**, instead of assuming. The rest
of the gate keeps running.

The 9 cases were seen red by restoring the old dereference: four of them printing `IT DIED`, which
is exactly what must not happen again.

> **And what this fix does NOT do, said out loud:** the three repos with a spec now report FAIL,
> because the gate reaches the end. That **has not been looked at** — it is a gate that had never
> been able to run in full, so its findings are new material, not a regression.

### §29-bis · And the new battery was born with the bug this file already documents

Adding it to the runner, the runner reported it **red: 4 OK · 5 FAIL** — while launched by hand it
gave 9 OK · 0 FAIL.

It was not the gate: it was **my battery.** Each case changes into a temporary directory before
launching the program, and I had stored the program's path **relative.** With an absolute path it
worked; called the way the runner calls it, the path no longer resolved after the change of
directory.

> **A test whose result depends on where you launch it from proves nothing.** It is trap **§7 of
> this very file**, committed in a battery written the same day I re-read it. That is why rules
> live in programs: knowing one is not enough.

## §30 · I removed 3 menu entries and left a dropdown with TWO

**Caught by:** the master gate's dropdown check, with 5 cases (red, green, and an FAQ accordion as
the negative control)

I took three items out of a mega-menu panel, and the reason was good: they were 3 of the 7 that
exist, hand-picked — a list inside a template that ages without anybody noticing. I measured before
cutting: all seven are linked from the body of their hub, so **no route was lost.**

What I did not look at is **what the panel was left with**:

| What stayed in the panel | Destination |
|---|---|
| "All agents, with real status" | the hub — **the same link as the parent** |
| The featured item's call to action | a page **already in the other panel** |

**Two links, and neither of them new.** A chevron promising a menu and delivering that costs two
gestures to go nowhere. **A human saw it by opening the site**; no program was looking.

**And the menu rule did not help, though it sounds as if it would:** it measures distinct chrome
destinations **over the whole site.** That day it dropped from 62% to 43%, so while the defect was
being created, **the menu rule was improving.** It never looks at the distribution INSIDE a panel.

> **The rule:** a dropdown with **fewer than 3 destinations is not a dropdown, it is a link.** If
> removing entries takes it below that, **it collapses to a plain link in the same batch.**

**Two decisions in the new check, and both are the difference between a gate and a nuisance:**

1. **Only controls inside a header or nav.** The relevant ARIA attribute is not exclusive to menus:
   an FAQ accordion uses it too, and its panels have **zero** links, entirely correctly. Without
   that bound, the gate would accuse the FAQs on all five sites — and a gate with false positives
   ends up ignored, which is worse than not having it. So the battery carries an **accordion
   fixture**: it does not check that the gate catches, it checks that **it does not bite what it
   should not.**
2. **The panel is cut with a depth counter**, not with a lazy match: mega-panels carry nested
   elements and the lazy version stops at the first inner close. The green fixture carries two
   nested wrappers on purpose so that a short cut **cannot pass.**

**Measured, not asserted:** production FAILED the check with *6 of 18 panels* right before the fix
went up, and PASSES with *16 panels* right after. Same command, half an hour apart.

### §30-bis · And the fix's own script counted capture groups, not matches

The program that collapses the block on the 21 hand-written pages (§24) aborts if a file does not
match **exactly once.** It aborted on all 21:

```
./index.html: the block matches 3 times (expected 1)
```

It did not match three times. `my $n = () = $html =~ /$re/g` in list context returns **the capture
groups of every match**, and the pattern had three groups: 3 groups × 1 match = 3. You count with
`$n++ while ...`, which counts what it says it counts.

> It is funny that the "all or nothing" rule saved it: a counter returning **triple** would have
> gone unnoticed in any "is there at least one?" check. **A plausible number is the worst error of
> all** — the same family as §16.

And the second abort is what validates the method: it expected **−1 closing tag** and got **−2**,
because the block closes two. Verifying **what you leave**, not only the absence of what you
remove, is §22.

## §31 · The layout primitive **was eating content**, silently

**Caught by:** `same-text.pl` — comparing the visible text against the previous tree, word by word.
**No instrument gate catches it** — it is the control you run by hand when you touch a layout.

Converting 29 pages from dumped prose into sections with roles, the text comparator produced **10
pages with loss, up to 207 words on a single one**: testimonial names, button labels (one call to
action four times), whole paragraphs.

Two holes in the card primitive, both from **assuming a shape the content does not have**:

| | What it assumed | What was there |
|---|---|---|
| 1 | A card starts at an image or a level-3 heading | Their cards are titled with **level-5 and level-6 headings.** With one at the start of the chunk, everything up to the first image fell through a `continue` |
| 2 | A card with no title is not a card | **A testimonial is text + photo + signature: it has no title.** All nine per city page were deleted |

**No error, no warning.** Valid HTML, gate green, and the page published with less text than it
arrived with. The house rule — *"you preserve the CONTENT, you rebuild the layout"* — was checked
by nobody.

> **What to take from it:** a new layout is verified **against the previous text, word by word.**
> Not against the number of sections, and not against the total word count — which would also have
> passed, because the hero adds two buttons — but against **which words** are there before and
> after.

### §31-bis · The section heading shipped with the ROLE NAME

When a chunk brought no heading, the section published titled **`qualification`**, **`process`**,
**`cta`**… and on the page whose blocks do not carry a top-level heading — because the theme
supplied it — it shipped literally **`<h1>hero</h1>`**.

Ten sections like that, on a client's live pages. **A heading with text in it is a perfectly valid
heading: zero checks look at it.** A human saw it in a phone screenshot; the text comparator only
caught the top-level one, because that was the only one that also *removed* their words.

> **The rule:** a role is OUR vocabulary, not the client's copy. If the content brings no heading,
> **the section ships without one.** An invented title is worse than none, and an ARIA label
> pointing at an id that does not exist also breaks the accessible name.

## §32 · One table with two uses: "related links" is NOT "parent"

**Caught by:** nobody. The breadcrumb rule checks that a visible breadcrumb **EXISTS**, not that it
**tells the truth.** **OPEN**

Breadcrumbs on one site hung menu pages off blog posts, and painted them with the **raw slug**:

```
Home / hypnosis-to-remove-a-third-person / Hypnosis
Home / compatibility-of-signs-in-love / Love tarot
```

One table served both **the footer's related links** and **the breadcrumb's parent.** A blog post
linking to a service is **recommending** it, not containing it. And since there is no menu label for
a post, the step's name fell back to the slug — **the clue was in plain sight and nobody read it for
what it was.**

**Two rules, and both come from the structure, not from a list:**

1. **It is only a hierarchy if the parent is IN THE MENU.** The menu is the structure of the
   business; what is not in it is not a level of the site.
2. **A page that is in the menu hangs off Home and nothing else.** Without this, the five sections
   that link to each other became each other's parents, and which one won depended **on hash
   ordering.**

> **And what matters most about this case: the defect was ALREADY in production before the batch.**
> I checked it against the previous copy before writing a line — which is §17's rule (render the
> BEFORE with the same flags) applied to data instead of to a screenshot. Without that check I
> would have "fixed" a regression I had not caused, and the diagnosis would have been different.

## §33 · An undeclared variable in a one-line replace deleted what it came to change

**Caught by:** the repair program itself, which **counts before and after and aborts if they do not
match** — which is what the original replacement should have done.

To make a heading conditional across six primitives I ran a one-line Perl replace interpolating two
variables. **Neither exists** in that program. Without strict mode — which a one-liner does not
have — Perl interpolates them **empty**: the first substitution **deleted the attribute** in all 7
primitives, and the second **deleted five whole heading lines.** Clean output, not a word of
warning.

> **It is §22 again**, and the lesson is the same written differently: **a bulk replacement has to
> check what it LEAVES.** Counting it is one line:
> `die "expected 7, replaced $n" unless $n == 7`.
>
> And the underlying one: **a one-liner has no strict mode, so any mistyped variable is the empty
> string.** If the replacement interpolates anything, it goes in a file with strict mode on, not on
> the command line.

## §34 · The spec auditor: three accusations, all three false

**Caught by:** its battery — 12 new cases, each fix with its red case, its green case, **and its
"this still fails" case.**

Going to wire it to the door, the first thing was to run it. **All five** repos reported FAIL. That
shape — everything broken at once — is the one that forces you to suspect the instrument, so I
opened the one I know best. **All three accusations were false:**

| Check | It said | It was |
|---|---|---|
| pages | 6 pages "declared and absent" | **5 are a retired shop section**, declared in the spec as withdrawn with its reason. The sixth is **the home page**: its record comes from the source with slug `"home"` and the gate looked for `home/index.html` |
| measurement | an attribute has no reader | **It was removed days earlier.** All that remains in the generator is the comment explaining why. **The gate was accusing the documentation of the fix of being the defect** |
| legal | "the spec declares no legal page" | It has **three**, published, with their text. The gate only looked at one collection, and that site uses it for something else |

And a fourth that appeared while fixing: **the measurement check would have failed any site for
declaring its anatomy.** The role attributes are written by the generator and read by **the gate**,
not by the browser. The check's rule — *"every emitted data attribute has a reader in the runtime"*
— is correct for a conversion marker and **exactly backwards** for an attribute whose reader is the
instrument. Without that exception, fixing a site's anatomy failed it.

> **The rule that comes out, and it is about gates, not sites:** a gate that is going to block has
> to recognise **the ways the thing it measures is genuinely declared**, not one single way. All
> three assumed one shape and called everything else a defect.

**And that is why it was wired in WITHOUT blocking.** A gate that has just produced three false
positives does not start preventing deploys the same day: it is wired so it can be seen, it gets
recorded in the history, it is watched for a few runs, and then the bar goes up. What you do **not**
do is leave it un-run, which is where it was. The reason and the date are in the deploy script's own
comment, not in anybody's head.

### §34-bis · And the door's battery caught my new step on day one

The new step recorded to the history **in dry runs too.** An existing case said so — *"a dry run does
NOT dirty the history"* — and it was right: the history is the record of what has been **published.**
If every dry run wrote, counting how many times a deploy shipped with a hole would stop being
possible.

> That is the third time a battery written for an earlier defect catches the next one **without
> anybody looking for it.** That is the return on writing them.

## §35 · The verdict said it and the **exit code was still 0**

**Caught by:** the receipt coverage battery — the case *"and it exits non-zero, not just says so"*

Half of §18 had been fixed: a lens that runs and measures nothing stops being sealed as approved and
the verdict says *"PASS · 1 lens NOT MEASURED: SEO"*. Measured afterwards:

```
VERDICT: PASS · 1 lens NOT MEASURED: SEO
  FAIL 0 · WARN 0 · ACCEPTED 0 · NOT VERIFIED 1 · PASS 0
exit 0                                        <- zero measured, and success
```

> **The suffix is read by a person. The exit code is read by everything else:** a shell `&&`, a
> deploy script, a scheduled task, an `if` in another program. Fixing the sentence and leaving the
> number is fixing **the half that is visible.**

**It exits 3, not 1, on purpose.** `1` is "I measured it and it is wrong"; `3` is "I did not measure
it." Whoever gets a `1` goes looking for the defect; whoever gets a `3` has to go and find out why
the lens could not measure — almost always the network, or a page not answering. Same distinction the
door makes between *not run* and *not verified*, and for the same reason: **sending somebody to look
for a defect that does not exist costs an afternoon.**

**The shape of the failure, which is what to take away:** the earlier fix was correct and tested —
three green cases — and still left the front door open, because the cases checked **what gets
printed** and nobody checked **what gets returned.** A battery looks at what it is told to look at.

## §36 · A documentation check said "does not apply" from the day it was written, and passed

**Caught by:** the documentation gate's battery — two new cases that measure **from the child
directory**, which is how it really runs.

Writing the new standard document, I went to check it with its own gate. It came out green. But the
line said:

```
PASS   D5   the paths carry the same block    fewer than 2 paths: does not apply
```

**It had not found a single path.** And there are four.

The check verifies that the four documents somebody **follows** name the deploy script, the only
mandatory door in the process. It exists because once they did not. And it had been **coming out
green without looking at anything** ever since.

**The cause, already in this file under another name:** the path documents live in the **root** and
the gate is launched from a subdirectory. The code **already looked at the parent** — it derived it
with a regex — but launched without an explicit directory, the value was `"."`, **a relative path with
no separator in it**, so the pattern did not match and the parent ended up being `"."` again.

And `"."` is exactly what it is when the runner calls it.

From the other side the mirror image happened: with an explicit root it finds the paths, but then two
other checks find neither programs nor traps. **The five checks had never run in the same pass.**

> It is trap **§29-bis** — *a test whose result depends on where you launch it from* — committed this
> time **in the documentation gate**, and with the same one-line fix: resolve to an absolute path
> before deriving the parent.

**And how it surfaced, which is the only reusable part:** no program found it. I found it **by reading
the line** instead of looking at the exit code. The gate said to its face what it had not looked at —
"does not apply" — just as the master gate says NOT VERIFIED. **That column exists to be read.**

## §37 · A new gate is measured against the LIVE estate before it is switched on

**Caught by:** the master gate's battery: 5 cases, **two of them decoys** that must NOT fire.

A new check was born to catch a whole family of defects that shipped as perfectly valid HTML, which
nothing was looking at:

```
<h1>hero</h1>                          the heading fell back to the ROLE name
<h2>qualification</h2>  ×10            same, ten sections
Home / hypnosis-to-remove-a-third… / Hypnosis    the breadcrumb painting the raw SLUG
[ field ] Do not fill in               the bot honeypot, in plain sight
```

**The rule is one line:** *what the visitor sees is their language, not ours.* A role is anatomy
vocabulary, a slug is a path, and "do not fill in" is an instruction for a robot.

### And then I measured it against the live sites before accepting it

| Site | What the check said | What the computed style measured |
|---|---|---|
| Site C, contact | honeypot visible | `x = -9999` · **visible: false** |
| Site A, home | honeypot visible | **0 such labels** in the DOM |
| Site D, contact | honeypot visible | `x=16 w=277` · **visible: true** |

**Two false out of three.** The correct way to hide a honeypot is `position:absolute; left:-9999px`
— some bots ignore `display:none` — and **that cannot be seen by reading the HTML.** The check was
accusing the well-built forms.

> **The rule that comes out, and it applies to any new gate:** before turning it into a `FAIL`, run
> it against every live site and look **case by case at whether it is right.** Passing the fixtures
> is not enough: **the fixtures were written by whoever wrote the check, and share its assumptions.**
>
> A gate that accuses two out of every three correct things **switches itself off**, and then it does
> not catch the real one either. Same as §23 and §34, except this time it was caught **before**
> switching it on and not after.

The honeypot rule is not thrown away: **it moves.** It belongs to the lens that measures with a
browser, where there is real geometry.

**After the trim: 5 live sites, 5 PASSES, zero false positives.**

## §38 · The migration gate counted images and called that "media"

**Caught by:** the source-inventory gate, a new block. **No test battery yet** — that program is not
in the runner, and that is the next hole in this same family.

Somebody looking at a home page: *"I think you removed the interactive video that was in the hero."*
I logged it as their decision — *"did you remove it or was it lost?"* — and they answered the only
thing that was needed: **"you're the only one who has touched that site."** They were right, and the
evidence was in the repo:

```
_migrate/source/media/hero-video.mp4                  2.9 MB
_migrate/source/pages/home.html:
  background_video_link":"https://…/hero-video.mp4"
  <video class="…-background-video-hosted" autoplay muted playsinline loop>
```

**Their hero had a background video. Our generator emits video nowhere.** I lost it in the migration.

### And why the gate closed saying nothing was missing

The source-inventory gate exists precisely to answer *"what did they have that we do not?"*, and it
closed that migration with **"2 holes, and both are tag manager containers."** Because its media block
enumerates **images.** Video, audio and embedded frames — maps, players, review widgets — **were
counted by nobody.**

Checked the same day in the three places it could have been: none of the three counted video.

**Any migration of ours could have lost a video, an audio file or an embedded map without anybody
noticing.**

> **And what to take from it, which is not "add mp4 to the list":**
> **the medium a page shows is not always in a media tag.** That video was **not** in a `<video src>`:
> it lived inside the page builder's settings, as a JSON property. A sweep for `<video>` would have
> come back clean and we would have closed just as comfortably. So the new block searches for **the
> extensions anywhere in the source** — attributes, embedded JSON, CSS — and not for tags.

### Two details that look like style and decide whether the check is worth anything

Both came out of testing it, and without them the block is decorative:

1. **The name must be preceded by a `/`.** Without requiring it, the expression matches inside
   minified JavaScript: `t.touchEvents.mov`, `a.mov`, `i.mov`, `r.mov`. **Four invented media in the
   first run.** A real medium always lives at a path.
2. **Our tree is searched WITHOUT the migration folder.** That is where the copy of their site lives,
   so searching the whole repo means **every medium of theirs is always found** and the gate is green
   by definition. In my first run the missing video came out as **ok** because of this.

**After both fixes: 6 of their media, 0 invented, and all 6 flagged as lost.** Which is the truth.

## §39 · I wrote a plan "measured against production" and five of its eight rows were false

**Caught by:** today, **NOBODY.** It is a trap about documentation, not code, and there is no gate that
checks whether a document tells the truth. The only thing that caught it was **going to execute the
plan and finding the work already done.**

I wrote a sprint plan with this header:

> *"Measured against production before writing this."*

**It was not.** Starting to execute it, row by row:

| Step | What the plan claimed | What was there |
|---|---|---|
| type attribute | "0 on the 4 client sites" | **One has it on 31 of 32 and production serves it.** Its generator even **aborts** if a page does not declare a type. Real: **two sites, not four** |
| six campaign pages | "2 sections each, no type" | **200, type declared, 9 and 11 sections.** They are fine |
| wire the anatomy | "the door runs 2 gates of 6" | Two checks **already go through the door**: they live in the master gate, which produces the receipt the door requires |
| a contact page | "the block is taller than the screen and pushes the form and the CTAs out of view" | At 390: CTA at y=418 and form at y=619, **both above the fold at 844.** The real problem is smaller |
| a rule | "pending" | **Implemented days earlier.** What is missing are its **cases: 0 in the battery** |
| a site | "do the logo and the form" | **Done days earlier**: logo on 42/42 pages. Blocked by the door with 8 FAILs, **3 legal and the client's** |

### The two shapes of the failure, which are different

**1 · I measured my own abbreviation.** In the plan I wrote the campaign URLs shortened, because they
are easier to read. And then I measured **that.** The short forms return **404**, and a 404 has 0
sections and no type attribute. That is where "2 sections" came from.

> And it nearly cost more: seeing five consecutive 404s I was one step from reporting **"the ad
> destinations are down"** — an alarm that would have sent somebody to review two ad accounts over
> something I invented. What stopped it was opening the spec and seeing that the real URLs are the
> long ones.

**2 · I marked as pending what was already done**, because I wrote it from memory instead of looking.
Three steps of eight were work finished days earlier — part of it, *mine*.

### Why it is worse than a bug

A wrong plan **does not fail: it directs.** Somebody read it, criticised it for something else, and
approved it. And they approved it because what they could check — the format, the links, the order —
**was fine.** The content, which they could not check without measuring, was false.
**A polished document passes a review exactly as well as a true one.**

### The rule, and it is a process rule because there is no program

1. **A row of a plan without its measurement next to it does not get written.** Not "I will measure it
   later": if measuring does not fit, the row is marked `NOT MEASURED` in the document itself. **A
   declared hole can be read; a covered one cannot.**
2. **No identifiers from memory.** URLs, slugs and paths are copied from their source, **even to read
   them more comfortably.** Today's abbreviation is tomorrow's false measurement.
3. **Before logging something as pending, look at whether it is already done.** A grep and a download
   cost seconds; executing work already done costs a session.
4. **The phrase "measured against X" is a verifiable assertion.** Either you paste the number and the
   command, or you do not write it.

## §40 · The runner skipped 5 batteries of 8 and kept saying "all green"

**Caught by:** the runner itself, with `</dev/null` on the line that executes each battery.

Wiring a new step that calls `ssh`, the count went from **413 to 273 cases**, **3 batteries of 8** ran,
and the last line still said:

```
  273 cases green · 0 red
  All batteries green.
```

### The cause

The battery list is read with a heredoc:

```sh
while IFS='|' read -r name cmd slow covers; do
  out="$( cd "$REF" && eval "$cmd" 2>&1 )"      # <- inherits the loop's stdin
  ...
done <<EOF
$BATTERIES
EOF
```

The loop body **inherits that stdin.** The new step calls `ssh`, and **`ssh` reads standard input by
default**: it ate the remaining lines of the list, and the following batteries never came into
existence.

### Why it is worse than a red battery

A red battery shouts. This one **disappeared**, and the runner read its absence as nothing to count.
The sentence "all batteries green" was literally true about the batteries that ran — and completely
false about what the reader understands.

Same family as §26: **the question is not "does it pass?", it is "what would have to happen for this
to go red?"** Here the answer was: nothing. **A battery that does not run cannot fail.**

### The rule

1. **Every loop that reads its list from stdin runs the body with `</dev/null`.** It is not defensive:
   `ssh`, `ffmpeg`, `mysql` and half a dozen others read stdin without being asked.
2. **A runner has to count the batteries it EXPECTED**, not just add up the ones that answered.
   *(Written here as pending when the trap was recorded. Verified since: the runner now counts the
   expected batteries before the loop and compares afterwards, and it also detects a battery that was
   written and never plugged in.)*
